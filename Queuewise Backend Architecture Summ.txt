Queuewise Backend Architecture Summary
🏗️ System Overview
We have successfully built a robust, real-time backend API for Queuewise using the MERN stack (MongoDB, Express, Node.js) combined with Socket.IO. The architecture is specifically designed to handle high-concurrency queuing with live updates and geospatial location services.

✨ Core Features Built
1. Secure Authentication & Role Management
JWT-Based Auth: Stateless, secure token generation (7d expiry).
Role-Based Access Control (RBAC): Users are strictly segregated into customer and owner roles. Owners are granted elevated privileges to create businesses and advance queues, while customers can only consume queuing services.
Password Encryption: All passwords are automatically salted and hashed using bcryptjs via Mongoose pre-save hooks.
2. Geospatial Business Directory
GeoJSON Location Storage: Businesses store exact longitude and latitude coordinates natively recognized by MongoDB.
2dsphere Indexing: We applied a spherical index to the business locations, enabling extremely fast, globe-aware distance calculations.
Smart Discovery: The GET /nearby route uses the MongoDB $geoNear aggregation pipeline to not only filter by category and a max-distance radius, but also dynamically calculate the exact distance (in meters) from the user to the business.
3. Smart Queuing Engine
Position Calculation: Instead of storing static arrays, the queue position is calculated dynamically based on the number of people currently waiting ahead.
Line Advancement (/next): Owners can advance the queue with a single endpoint that gracefully transitions the front user to in-service, logs their completion time, and calls the next person up.
Dynamic Re-shuffling: If a user cancels or leaves the queue early (/leave), the system loops through everyone else waiting and automatically subtracts 1 from their position.
4. Real-Time Socket.IO Integration
Event-Driven Architecture: The Express REST API seamlessly hands off to Socket.IO right after database mutations occur.
Targeted Rooms:
Business Rooms: Broadcasts full queue lists to dashboards/displays (queueUpdated).
Private User Rooms: Sends targeted push updates to individual phones when their specific position changes (yourPositionUpdated).
🚀 What Makes This Unique?
TIP

The Rolling Average Algorithm Most queuing systems use static, hardcoded wait times (e.g., "every haircut takes 15 minutes"). Our system dynamically updates the business's avgServiceTimeMinutes every time the owner clicks "Next".

By using a weighted moving average (80% historical data + 20% recent service time), the application learns how fast the business operates today. If a clinic gets exceptionally busy or doctors are running slow, the estimated wait times for incoming users automatically inflate to reflect reality!

NOTE

Decoupled Real-Time Sync By forcing clients to join specific Socket rooms rather than broadcasting globally, we've built a highly scalable real-time system that doesn't waste bandwidth sending updates to users who don't care about them.

🔧 How It Can Be Done Better (Future Improvements)
While the current architecture is incredibly solid, here are ways we can scale it as the application grows:

1. Redis Caching
The Problem: Querying QueueEntry.countDocuments every time someone joins, or recalculating positions for 50 people when someone leaves, requires direct disk-reads from MongoDB.
The Solution: Store the active, live queue lines in Redis (an in-memory datastore) as a fast List or Sorted Set. Only write to MongoDB once a user completes their service for historical logging.
2. Geohashing / ElasticSearch
The Problem: MongoDB's $geoNear is fast, but if the database grows to millions of businesses, running aggregations directly on the primary database will slow it down.
The Solution: Migrate the search functionality to ElasticSearch, or implement basic Geohashing so users only query businesses within their specific sector grid.
3. Push Notifications & WebSockets Fallback
The Problem: If a user locks their phone screen, iOS/Android will often suspend the browser tab, severing the Socket.IO connection.
The Solution: Integrate Firebase Cloud Messaging (FCM) or Web Push API. If a socket disconnected but it's their turn to be seen, the server can fire a literal Push Notification to their device ("It's your turn! Head to the counter.").
4. Rate Limiting & Queue Throttling
The Solution: Implement express-rate-limit to prevent malicious users from spamming the /join and /leave endpoints rapidly, which currently triggers expensive position recalculations and socket emits.
5. Multi-Service Capabilities
The Problem: Right now, a business is a single queue.
The Solution: Allow businesses to have multiple "Desks" or "Providers" (e.g., a salon with 5 different barbers). The model could be expanded so a user joins a specific Barber's queue, or joins a pooled queue where the first available barber takes them.
